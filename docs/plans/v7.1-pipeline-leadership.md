# Pipeline leadership: dispatch budget, supervisor contract, Lean file gate, bash-guard precision

**Status:** IMPLEMENTED 2026-09-29 on `feature/v7.1-pipeline-leadership` (test-codex-adapter §131–§134 green; bump pending user go-ahead). Deviations from this spec, all deliberate: (a) item 1 is per TASK, not per phase (the measured churn crosses phase boundaries); (b) `mv /tmp/x src/x` now BLOCKS — `mv` counts its source and `/tmp` is not sanctioned (the scratchpad is), §44 updated; (c) a heredoc that feeds an interpreter IS scanned for write calls (the spec said "data"; `python3 - <<PY` with `open('/etc/x','w')` must block); (d) the 4 KB / 3-heredoc parse measures ≈120 ms under bash 3.2, not the <50 ms written here — the cost is `realpath` per target, acceptable for a hook; (e) `Q4` is refused as `untagged`, not `question-invalid`; (f) `APD_WALL_NUDGE_SEC` has no floor (the value is the operator's; tests use 1 s).
**Type:** minor (v7.1.0): one new pre-spawn gate, one contract extension, one opt-out condition, one guard rewrite
**Enforcement impact:** items 1–3 are STRICTER or additive; item 4 removes FALSE blocks only and must prove, per class, that the true write of the same shape still blocks

## 1. Dispatch budget: count dispatches, not advances

### Problem
Between two `pipeline-advance` calls the orchestrator may dispatch any number of agents. The cap it can hit is on advances, so the churn that costs hours (builder → reviewer → builder → reviewer inside one phase, plus post-adversarial fix rounds) is invisible to the gate.

### Mechanism
A **per-task** budget by role class, enforced **pre-spawn** in the existing `PreToolUse(Agent)` guard (`bin/core/guard-agent-reload` runs there and is the proven pre-spawn point since v6.27). Per-task, not per-phase, because the measured churn crosses phase boundaries: the fix rounds after `builder.done` are where "Token storage" spent rounds 2–4.

- **Source of truth:** `.apd/pipeline/.agents` start events since `spec.done` (same window and same `SPEC_TS_HUMAN` compare as `_scan_builder_ran`). No new state file: the ledger already exists, is wiped on spec re-advance and reset, and survives rollback, exactly the cap semantics workflow.md §0b documents.
- **Role class of the dispatch being requested:** from `tool_input.subagent_type` in the PreToolUse payload, resolved with `_agent_def_file` (`bin/lib/agent-scope.sh`):
  - `builder` class = a project-defined agent that `_agent_is_writable` says can write (builders, docs-writer, test-guardian, database…);
  - `reviewer` class = name matches `review` and not `adversarial` (today: `code-reviewer`);
  - `adversarial` and `supervisor` keep their existing caps (supervision churn cap = 2 stops, v6.30); the adversarial pass gets a budget of **2 dispatches** here (starts, like the other classes — a dropped stop must not uncount a real pass), same shape;
  - agents APD does not own (`Explore`, `general-purpose`, `fork`, plugin agents) are not counted: they cannot advance a phase.
- **Defaults** (calibrated on the table above; every healthy run in the corpus fits, every marathon does not):

  | Class | Default per task | Runs it would have stopped |
  |---|---|---|
  | builder | 12 | Dokumentacija f.3 (12, at the line), Posta drain (26), Pickup window (28) |
  | reviewer | 6 | Posta drain (6, at the line), Token storage (4, passes) |
  | adversarial | 2 dispatches | none in the corpus (Token storage ran 2) |

- **Override** in the signed spec (spec-time, same idiom as `max_cycles`):
  ```
  dispatch_budget: builder=N reviewer=M adversarial=K
  ```
  and in flight, **without re-signing**, the existing valve extended with a third phase word:
  ```
  bash .claude/bin/apd pipeline raise-cap dispatch <builder|reviewer|adversarial> <N|unlimited> "<reason>"
  ```
  written to `.apd/pipeline/.dispatch-cap-override` (one line per class, last wins), reason mandatory, logged `INFO|cap-raise|phase=dispatch:<class> new=N reason=…`. Raises only.
- **Block:** count of starts for that class in the task window + 1 > budget → `exit 2` (pre-spawn, the dispatch never happens), stderr names the class, the count, the budget, the three ways forward in this order: **spinoff / decompose** (`apd pipeline spinoff-finding`), `raise-cap dispatch … "<reason>"`, `apd pipeline reset`. `log_block "dispatch-budget-exceeded" "class=<c> count=<n> budget=<b> task=<task>"`.
- **Wall-clock nudge (INFO, never blocks):** at every `pipeline-advance <phase>` and at the first dispatch after crossing the line, when `NOW − SPEC_TS > APD_WALL_NUDGE_SEC` (default 5400 = 90 min): one line naming elapsed time, dispatches so far by class, and "consider spinoff / decompose". Stateless throttle at the dispatch guard: fire only when the previous start in `.agents` was still under the line. Logged once per crossing as `INFO|wall-clock-nudge|elapsed=<h:m> builder=<n> reviewer=<m>`.
- **`apd pipeline status`** gains a line: `dispatches: builder 7/12 · reviewer 3/6 · adversarial 1/2`.

### Contract and limits
- CC-only (the Agent tool and PreToolUse are CC concepts). Codex: honest-inert, no counter, documented as such, the same posture as the v6.33 supervision gate.
- Parallel dispatches issued in ONE assistant message each see the same ledger count, so the budget can be exceeded by the parallel width of that one message. `parallel-same-agent` (30 s window) already blocks same-type parallelism; different-type parallel dispatches are legitimate and each still counts on the next check. Stated in code and SPEC, not hidden.
- Dropped `SubagentStop` events do not matter (starts are counted); `reconstruct-agents` rebuilds starts too, so a rebuilt ledger keeps the budget honest.
- The pre-spawn shim (`bin/adapter/cc/guard-agent-reload`) currently drains stdin. It must now parse `tool_input.subagent_type` and pass it as `--subagent-type`; when the field is absent (older CC payload shape) the budget check is skipped and `INFO|dispatch-budget-unmeasured` is logged once. The reload gate's own behaviour is unchanged.
- `guard-agent-reload` becomes two checks in one script (marker, then budget), in that order; the reload block keeps its exact message and exit.

### Red-green (test-codex-adapter §131)
Each mechanism gets a test that FAILS when it is removed:
1. fixture `.agents` with 12 builder-class starts in-window → 13th `PreToolUse(Agent)` payload for a writable agent → exit 2, reason `dispatch-budget-exceeded`; the SAME payload with 11 starts → exit 0.
2. reviewer class at 6/6 → exit 2; adversarial at 2/2 → exit 2; `Explore` at any count → exit 0 (not counted).
3. starts dated BEFORE `spec.done` do not count (pre-spec filter).
4. spec-card `dispatch_budget: builder=20` → 13th allowed; `raise-cap dispatch builder 20 "reason"` → allowed, `.dispatch-cap-override` present, INFO logged; `raise-cap dispatch builder 20` with no reason → exit 1, nothing written; a LOWER value than the current budget is refused (raises only).
5. `spec` re-advance wipes the override; `reset` wipes it.
6. wall-clock: `spec.done` timestamp 91 min old → `pipeline-advance builder` output contains the nudge line and one `wall-clock-nudge` INFO; 60 min old → neither.
7. payload without `subagent_type` → exit 0 + `dispatch-budget-unmeasured` INFO (once).
8. mutation: comment out the budget block → tests 1, 2 flip red; comment out the pre-spec filter → test 3 flips red.

## 2. Supervisor contract: findings carry the question they answer, notes need no disposition

### Problem
The supervisor charter limits it to four questions, but the output format only knows "findings", and the verifier's rationale contract forces a disposition for every one. Anything the supervisor noticed but that answers none of Q1–Q3 (spec wording, a stale comment, a missing RS declaration) enters as a finding, is accepted because accept is cheapest, and then costs a spinoff, a builder round or a second supervisor pass.

### Mechanism
- **Template (`templates/supervisor-template.md`):** each finding line becomes
  ```
  1. [Q1 R3 / src/x.cs:41] — Final diff no longer satisfies R3: <what changed>
  2. [Q2 / src/y.cs:12] — Collateral of the fix for adversarial finding 2: <what>
  3. [Q3 RS1 / tests/z.cs] — Regression surface claim inconsistent with diff: <how>
  ```
  and a new section **after** `### Findings`:
  ```
  ### Notes
  - <anything outside Q1–Q3: wording, style, stale comments, declaration gaps>
  ```
  with the rule spelled out in the charter: a Note is NOT a finding, needs no disposition, never triggers a fix or a second pass, and is copied verbatim by the orchestrator under the `SUPERVISION:` line of `.supervision-summary` (that file already carries "+ Notes").
- **Rationale contract (`.supervision-rationale.md`)** gains one required field per finding, supervision-only (the adversarial contract is untouched):
  ```
  ## Finding N — <title>
  **Question:** Q1 R3 | Q2 | Q3 RS1
  **Severity:** …
  **Status:** …
  **Rationale:** …
  ```
- **Gate (`_supervision_issue`)**, new checks in the existing order after the field-count check:
  - every `## Finding` block has exactly one `**Question:**` line → else `supervision-rationale-untagged|found=<k> expected=<T>`;
  - `Q1 R<n>`: R<n> must be one of the spec's R-ids (`_count_criteria`'s pattern, de-duplicated) → else `supervision-question-invalid|Q1 R<n> not in spec`;
  - `Q3 RS<n>`: RS<n> must exist in the spec's `**Regression surface:**` block → else `supervision-question-invalid|Q3 RS<n> not declared`;
  - `Q2`: the path in the finding must appear in `.apd/pipeline/.reviewed-files` (it IS the diff scope) → else `supervision-question-invalid|Q2 path not in reviewed scope`.
  - `T` in `SUPERVISION:T:A:D` counts tagged findings only; Notes are not counted and not validated.
- **Why the anchor and not just the tag:** a tag alone is one word to type. Tying Q1 to a real R-id, Q3 to a declared RS-id and Q2 to a file in the diff makes a note-dressed-as-finding a false claim the orchestrator can dismiss with rationale, and the archive shows it. It does not make a real finding harder to file.
- Everything else stays: finality, the 2-stop churn cap, the dispatch-backed pass, `supervision-pass` / `supervision-warn` telemetry, no spec-card opt-out.

### Rollout
The supervision gate is still `SUPERVISION_GATE_DEFAULT="warn"`, so the new codes are advisory by construction until the strict flip; they ride the same one-line switch. Existing projects have a copied `supervisor.md`: `apd-init` treats a missing `### Notes` marker as stale content and refreshes from template, preserving profile-managed `model:`/`effort:` (same idiom as the v7.0 `guard-spec-blind` marker); `/apd-setup` step 5c reports it as drift.

### Red-green (§132)
1. rationale with 3 tagged findings, all anchors valid → `_supervision_issue` prints nothing.
2. one block without `**Question:**` → `supervision-rationale-untagged`.

## 3. Lean opt-out: the file count the doc already promises

### Problem
`_adversarial_opt_out_ok` honours `adversarial: skip` at ≤2 R-criteria only. workflow.md §0 states the second condition ("fewer than 5 files in scope") that nothing measures. 164 files went through Lean.

### Mechanism
- `_adversarial_opt_out_ok` gains the second condition: if `.apd/pipeline/.reviewed-files` exists, its non-empty line count must be **< 5** (`ADV_OPT_OUT_MAX_FILES=5`, one constant, the doc's own number). Same function is evaluated at the reviewer step and re-evaluated at the verifier, so both agree by construction (that symmetry is a v7.0 invariant).
- At the reviewer step `_write_reviewed_files` moves BEFORE the opt-out decision (it is idempotent; today it runs after `create_done`). The refresh after `create_done` stays.
- Denial path mirrors the existing R>2 denial: `warn "Adversarial opt-out DENIED: N files in scope (max 4 for opt-out)"`, `.adversarial-pending` written, Full mode continues. Plus, new for BOTH denial reasons (the R>2 path logs nothing today): `INFO|adversarial-opt-out-denied|criteria=<n> files=<m>`. The strict-flip window for this gate needs the count of denials, as supervision's did.
- Non-git project (no `.reviewed-files`): unchanged (R-only), logged once `INFO|adversarial-opt-out-files-unmeasured`. `.reviewed-files` cannot be edited by the orchestrator (pipeline-state guard, not on the Write/Edit allowlist) and is regenerated at the decision point, so the measurement is not the orchestrator's to game.

### Red-green (§133)
1. 2 R + `adversarial: skip` + 4 reviewed files → opt-out honoured (no `.adversarial-pending`).
2. 2 R + skip + 5 reviewed files → denied: `.adversarial-pending` present, warn text names `5 files`, INFO logged; verifier then requires the pass (symmetry).
3. 3 R + 2 files → denied on criteria (unchanged) and INFO now logged with `criteria=3 files=2`.
4. no `.reviewed-files` → honoured + `unmeasured` INFO.
5. mutation: drop the file condition → test 2 flips.
6. `verify-apd` Section 8 synthetic run stays green (its opt-out fixture has < 5 files; assert that number so a future fixture change cannot silently flip the gate; add to the §71 lock-in list).

### Docs
guide CC + Codex (the opt-out sentence gains "and fewer than 5 files in the reviewed scope"), `rules/workflow.md` §0 "Opting into Lean" (mechanical cap now names both conditions), `docs/SPEC.md` §5 reviewer step + §2 Lean line, `templates/codex/AGENTS.md` + `rules/brainstorm.md` where the opt-out is described.

## 4. `guard-bash-scope`: right caller in the log, and a parser that reads shell as shell

### 4a. Caller attribution (trivial, first)
`bin/adapter/cc/guard-bash-scope` reads `agent_type` from the payload and never exports it; the core's `log_block` therefore prints `${AGENT_ID:-orchestrator}`. Fix: the adapter extracts `agent_id` as well and `export AGENT_TYPE AGENT_ID` before every `exec` (all five exec sites). Expected line: `…|BLOCK|a3cb0757(frontend-builder)|out-of-scope-bash-write|…`. Codex payload carries no role → stays `orchestrator` (correct there). Also raise the logged command excerpt `${COMMAND:0:100}` → `${COMMAND:0:200}` at every `log_block` in this guard: the 100-char cut hid every cause in this analysis.

Red-green: payload with `agent_type=frontend-builder`, `agent_id=abc` and a blocked command → audit line contains `abc(frontend-builder)`; without `agent_type` → `orchestrator`. Mutation: remove the export → flips.

### 4b. Parser: classes, fixes, and the true write that must still block

Design rule for every class: the guard must decide from what the SHELL would do, not from substrings. One pass, pure bash 3.2 + awk (the guard runs on every Bash call under a 5 s Codex timeout; no python, no external tools beyond the coreutils already used). Measured budget: < 50 ms on a 4 KB command.

**Shared normaliser.** `_path_in_scope` currently prefix-matches the raw token against relative scope roots. Move the canonicaliser from `guard-scope` (realpath of the deepest EXISTING ancestor + re-attached tail, `PROJ_CANON`, v7.0.4) into `bin/lib/path-canon.sh` and use it in both guards. A target is then in scope when its canonical form is under `PROJ_CANON/<scope>/`: absolute or relative, symlinked or not, existing or not yet.

### What this does not fix, said openly
- `[[ $a > $b ]]` string comparison outside quotes reads as a redirect (rare in agent commands; documented, not handled).
- Process substitution `>(cmd)` and `exec 3>file` are treated as redirects to a target named `(cmd`/`file`. The former is a false block, kept because handling it means parsing subshells; the latter is correct.
- The Write tool cannot target the scratchpad (`guard-scope`, "outside the project"): out of this spec. The bash channel now can, which is the sanctioned route.

### Red-green (§134)

The suite must run the rows under `/bin/bash` on Darwin (§122 pattern), because the tokenizer is exactly the kind of code where 3.2 and 5 diverge.
